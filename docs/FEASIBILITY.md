# Flash 游戏数值修改可行性分析

> 本文回答：修改 Flash 游戏的**血量 / 金钱 / 伤害**等数值，技术上是否可行、用哪条技术路线、
> 能覆盖多少游戏、哪些场景做不到。结论先行：

**结论：可行，且在"Ruffle(WASM) 运行时 + 进程内扫描"这条路线上可以做成完全通用的工具，
无需针对单个游戏做任何逆向配置。血量、金钱类持久变量最容易；伤害类瞬态数值中等难度；
加密/混淆数值困难。**

---

## 1. Flash 游戏数值在内存中的真实形态

Flash 内容运行在 AVM（ActionScript Virtual Machine）上，分两代：

| 运行时 | 脚本版本 | 数值表示 | 对扫描的影响 |
| --- | --- | --- | --- |
| AVM1（老游戏，约 2000–2008，占存量大多数） | ActionScript 1/2 | 所有 `Number` 都是 **IEEE754 双精度（f64）** | 用 f64 扫描即可命中 |
| AVM2（新游戏，2006+） | ActionScript 3 | `Number` 是 f64；`int/uint` 在对象槽位与寄存器中常以 f64 存储，进入 Rust 侧结构体后可能是 **i32/f32** | f64 + i32 + f32 三种类型覆盖 |

关键事实：**游戏里显示的"血量 100"，在内存中几乎总是一个 f64 的 `100.0`（或 i32 的 100）**，
与 Cheat Engine 扫描原生游戏的情形一致。这就是"通用修改器"可行的物理基础。

## 2. 四条技术路线对比

### 路线 A：外部进程内存扫描（Cheat Engine 式）❌ 不选

针对独立 Flash 播放器/浏览器进程用 ReadProcessMemory/WriteProcessMemory 扫描。

- 需要外部驱动原生 API，Windows 下要处理 ASLR、权限、UAC；
- Flash Player 已停止分发，Ruffle 桌面版是 Rust 程序，值深埋在 Rust 结构体里，**指针路径不稳定**；
- 工具形态上必须依附第三方软件，做不到开箱即用的通用性。

### 路线 B：Ruffle WASM 线性内存扫描（本项目采用）✅

Ruffle（Rust 编译为 WASM 的开源 Flash 模拟器）在 JS 侧的 `WebAssembly.Memory` 暴露为
**可读写的 ArrayBuffer**。只要在加载 Ruffle 之前替换 `WebAssembly.Memory` /
`WebAssembly.Instance` 构造器，就能捕获播放器的全部线性内存，之后：

- **扫描** = 对 ArrayBuffer 做 TypedArray 遍历（f64/i32/f32 对齐扫描）；
- **修改** = DataView 直接写回，游戏下一帧读到的就是新值；
- **锁定** = 定时器持续写回，覆盖游戏每帧的改写；
- **变速** = 包装 `performance.now` / `Date.now` 缩放游戏时间。

优势：

1. **完全通用**：不解析字节码、不需要每游戏配置，工作流与 Cheat Engine 相同
   （首扫 → 改变数值 → 再扫收敛 → 写入/锁定），对绝大多数"数值存变量"的游戏有效；
2. **零权限**：纯 JS 操作自己进程内的内存，无需管理员权限、无需驱动；
3. **跨 AVM1/AVM2**：Ruffle 同时模拟两代虚拟机，所以老 AS2 游戏和新 AS3 游戏都适用；
4. 工程上干净：Electron + React 全栈 TypeScript，无原生模块。

### 路线 C：SWF 字节码补丁（RABCDAsm/FFDec 式）✅ v1 已落地（常量级）

离线修改 SWF 文件本身，让修改永久生效。v1 已实现**常量级补丁**：

- **AS3(AVM2)**：遍历 DoABC/DoABC1 标签，在 ABC 常量池内定位——double 池（8 字节
  IEEE754，原地改写）与 int/uint 池（u30 变长，新旧值编码等长时原地改写，不等长跳过并报告）；
- **AS2(AVM1)**：PushDouble/PushFloat 内联字节按双精度/单精度模式全文件匹配改写
  （仅在文件不含 ABC 标签时启用，避免与常量池重复命中）；
- 4 字节整数不做全文匹配（误伤率过高）；LZMA(ZWS) 暂不支持；
- 输出保持原压缩方式（FWS 直存 / CWS 重压缩），始终另存为新文件。

UI 入口：修改列表 →「写入 SWF」→ 勾选条目（可编辑原值）→ 分析命中数 → 另存为。
命中数为 0 说明文件内没有该值的常量（运行时计算得出或数值不落地），属预期行为。

永久化改"伤害公式"这类逻辑仍需完整反编译（FFDec 级别），是后续方向。

### 路线 D：AVM 运行时桥（ExternalInterface）❌ 不可依赖

Ruffle 出于安全只开放极小的 JS↔AVM 桥，且要求游戏自己暴露接口，不通用，放弃。

## 3. 逐项可行性

| 目标 | 可行性 | 说明 |
| --- | --- | --- |
| **血量 (HP)** | ★★★★★ 容易 | 典型持久变量。受伤后数值变化 → "未知初始 + 减小了" 或 "精确值" 两三轮收敛 |
| **金钱/资源** | ★★★★★ 容易 | 同上；消费后"减小"、拾取后"增大"皆可收敛 |
| **伤害** | ★★★☆☆ 中等 | 分两类：**攻击力属性**（持久，容易）；**单次伤害结算值**（瞬态，产生即参与计算，扫描窗口短）——技巧是先打出一次伤害记住数字，用"未知初始 → 精确值/介于"在结算瞬间连续扫描，或直接改攻击力属性达成目的 |
| **经验/等级/分数** | ★★★★☆ 容易~中 | 分数类通常持久；部分游戏在显示层做了缩放（如内部 100 显示为 1），用"未知初始 + 增大"流程不受显示换算影响 |
| **时间/倒计时** | ★★★★☆ 容易 | 数值持续变化，"减小了"链式收敛非常有效；或直接用变速齿轮 |
| **加密/混淆数值** | ★★☆☆☆ 困难 | 少数网页游戏对数值做异或/校验（改了就崩）。此时精确扫描失效，只能靠"变动/未变动"差异扫描碰运气，或走路线 C 补丁 |
| **锁定（无敌/无限金币）** | ★★★★★ 容易 | 50ms 周期写回即可覆盖绝大多数按帧改写的逻辑 |
| **变速** | ★★★★☆ 容易 | 影响帧循环与计时器（游戏主逻辑）；AS 的 `Date` 类走 OS 时钟不受影响（见架构文档） |

**已知限制（如实声明）：**

1. 扫描出的地址是**会话内有效**：重启游戏后 WASM 堆布局可能变化，地址失效。
   本工具按游戏内容 SHA-256 保存修改配置并在下次加载时**自动校验失效条目**，
   但不能像 CE 指针扫描那样保证跨会话稳定。
2. 值不存在于 AVM 堆的（例如直接绘制、纯 GPU 计算）扫不到——Flash 时代这类游戏极少。
3. 依赖 Ruffle 的模拟完备性：个别重度使用 Director/AS2 深层特性的游戏可能本身跑不起来，
   这属于 Ruffle 上游兼容性问题，不是修改器问题。

## 4. 合规与边界

本工具仅操作**本机、本地、单机**Flash 内容的自身进程内存，用于学习研究游戏内部实现、
备份老游戏进度。不接触网络对战、不破解付费/DRM、不注入他人进程。分发时保留 MIT
许可证与免责声明即可。

## 5. 落地结论

按路线 B 实现，工程结构见 `docs/ARCHITECTURE.md`，操作教程见 `docs/USAGE.md`。
核心扫描引擎 `src/renderer/src/core/scan/engine.ts` 与 25 个单元测试保证了
Cheat Engine 全套扫描语义（精确/介于/未知初始/增大/减小/变动/未变动 + 撤销 + 上限保护）
的正确性。
